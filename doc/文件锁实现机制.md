# swinx 文件锁实现机制说明

> 适用范围：`swinx/src/sharedmem.h`（`TSemRwLock`，统一实现：移动端匿名 / 桌面端 fcntl）、`swinx/src/sharedmem.cpp`、`swinx/src/sysobjs.cpp`
> 日期：2026-09-09（最近一次重构：TSemRwLock 合并 TNamedSemRwLock / TAnonymousRwLock 为单类，移动端/桌面端两实现）。Linux / macOS 全部 fun_test 用例（含 `swinx_flock.*` 回归套件）通过。

---

## 1. 背景：为什么要替换信号量

swinx（Win32 兼容层）的命名内核对象（事件/互斥锁/信号量/计时器/文件映射）依赖一组跨进程锁：

| 锁 | 原实现 | 用途 |
|---|---|---|
| `TSemRwLock<kSharedNumber>`（SharedMemory 全局句柄表） | POSIX 命名信号量（`sem_open`/`sem_wait`/`sem_post`） | 保护全局句柄表所在的共享内存（`GLobalHandleTable`，静态全局对象，**main 之前**构造） |
| `TSemRwLock<1>`（`GlobalMutex`） | XSI System V 信号量（`semget`/`semop`） | 每个命名对象/文件映射对象的内部状态互斥（key = 表基 key + 槽位 + 10000） |

> 注：`TSemRwLock` 现为 swinx **唯一的** rwlock 类型，不再有 `TNamedSemRwLock` /
> `TAnonymousRwLock` 别名。它用同一个模板类同时通过 `init(uint32_t key)` 与
> `init(const char* name)` 两个重载覆盖"按 key"与"按名"两种调用；移动端
> （Android/OHOS/iOS）与桌面端（Linux/macOS）分别提供实现（见 §2.1）。

两类信号量有一个共同的致命弱点：**内核状态在进程退出后不自动恢复**。

- 命名信号量的计数被 `sem_wait` 拉空后，若持有进程在 `sem_post` 之前崩溃（或被 kill，来不及走析构），信号量计数停留在 0；
- XSI 信号量集同理，`IPC_RMID` 只在对象析构时调用。

后果：**下一个启动的进程会在同一把锁上永久阻塞**。对 `TSemRwLock<kSharedNumber>`（全局句柄表）而言，阻塞点在 `GLobalHandleTable` 的全局构造函数里——发生在 `main()` 之前，程序连一条日志都来不及打印就"起不来了"。这正是 leak.log 中 `sem_wait ← TSemRwLock<kSharedNumber>::lockExclusive ← SharedMemory::init ← __cxx_global_var_init` 调用栈的成因。

## 2. 方案：fcntl POSIX 记录锁

两个锁类的内部实现全部替换为 **fcntl 记录锁**（`fcntl(fd, F_SETLKW, &flock)`），核心利用其一个内核级契约：

> **记录锁与持有进程绑定，进程终止（无论正常退出还是崩溃/被 SIGKILL）时由内核自动释放。**

残留的锁**不可能**再阻塞下一次启动——崩溃后锁文件还在，但锁状态已随进程消失。

### 2.1 锁文件映射

| 锁类 | 锁文件路径（仅桌面端） | 标识来源 |
|---|---|---|
| `TSemRwLock<k>`（name 重载） | `/tmp/soui_flock_<净化名>.lock` | 共享内存/对象名（如 `/share_soui_…`，非 `[A-Za-z0-9_-]` 字符统一替换为 `_`，杜绝路径穿越） |
| `TSemRwLock<k>`（key 重载） | `/tmp/soui_flock_key_<key十进制>.lock` | 整数 key（同一命名对象跨进程计算结果一致，与 `semget(key)` 同步到同一信号量集等价） |

平台实现差异（同一模板类，两分支）：

```cpp
#if defined(__ANDROID__) || defined(__OHOS__) || defined(__IOS__)
    // 移动端：进程内匿名读写锁（std::mutex + std::condition_variable），
    // 不创建任何锁文件，init 永不失败。单进程 App 无需跨进程互斥。
    template <int kNumLock = 2> class TSemRwLock : public ISemRwLock { ... };
#else
    // 桌面 POSIX（Linux/macOS）：fcntl 记录锁，锁文件固定位于 /tmp/。
    template <int kNumLock = 2> class TSemRwLock : public ISemRwLock { ... };
#endif
```

> **为什么移动端不再用文件锁**：移动沙箱（尤其鸿蒙应用沙箱）内 `/data/local/tmp`
> 常不可写；而移动端为单进程，全局句柄表只需进程内共享。若仍用命名 fcntl 文件锁，
> `init` 时 `open` 锁文件失败会令全局句柄表失效、进而运行时 `getRwLock()` 返回空指针
> 崩溃。改用匿名锁 + `SharedMemory` 的堆内存回退即可根治（见 swinx 共享内存移动端
> 适配说明）。桌面端保留 `/tmp/soui_flock_*.lock` 以支持跨进程互斥。

两个设计要点：

1. **锁文件绝不 unlink**。fcntl 锁绑定在 (进程, inode) 上：若其它进程正持锁时删除路径，后续进程 `open` 会创建新 inode，旧持锁者的锁就管不到新进程，互斥被破坏。残留的 `.lock` 文件不携带任何锁状态，无害。
2. **`O_CREAT | O_RDWR` 幂等打开**。取代原 XSI `IPC_CREAT|IPC_EXCL` 探测 + `EEXIST` 回退的分支；且原 XSI 版每个进程 `init` 时都会 `SETVAL=1` 重置计数（会破坏其它进程已持有的锁状态），文件锁天然没有这个问题。

### 2.2 语义映射

| ISemRwLock 接口 | fcntl 操作 | 语义 |
|---|---|---|
| `lockExclusive` | `F_SETLKW F_WRLCK` | 排他：与读写双方互斥 |
| `unlockExclusive` | `F_SETLKW F_UNLCK` | 释放 |
| `lockShared` | `F_SETLKW F_RDLCK` | 共享读：多个读者可并发（跨进程） |
| `unlockShared` | `F_SETLKW F_UNLCK` | 释放 |

模板参数 `kNumLock`（`<5>` / `<1>`）仅保留为调用点签名兼容（`SharedMemory` 用 `TSemRwLock<kSharedNumber>`、`GlobalMutex : TSemRwLock<1>`），记录锁不需要槽位计数，以 `static_assert` 引用满足 `-Wall -Wextra`。

### 2.3 进程内线程串行化层（FlockGateState）——关键配套设计

fcntl 记录锁的所有权属于**进程**而非线程，这带来两个与原信号量行为不同的地方：

1. 同进程任何线程发起 `F_SETLKW` 都立即成功（进程已持锁）；
2. 任一线程的 `F_UNLCK` 会释放整个进程的锁，即使另一线程仍在临界区内。

而被替换的 `sem_wait` 按计数阻塞，**同进程多线程之间、以及同进程映射到同一信号量的多个锁对象实例之间同样互斥**。若只用裸文件锁，多线程应用对同一命名对象的并发访问（如两个线程同时对同一命名信号量 Set/Wait）将失去互斥——这是纯文件锁方案的功能回归。

解决方式：以锁文件路径为 key 维护**每路径一份进程内状态**（`FlockGateState`，函数局部静态保证可安全用于全局构造期）：

```
lockX():  gate.lock()                      ← 线程间互斥（等价旧 sem_wait 进程内阻塞）
          opMutex.lock();
          if (holders++ == 0) F_SETLKW     ← 本进程第一个持有者负责加文件锁
          opMutex.unlock();

unlockX(): opMutex.lock();
          if (--holders == 0) F_UNLCK      ← 最后一个持有者退出才释放文件锁
          opMutex.unlock();
          gate.unlock()
```

性质：

- **线程间互斥恢复**：与原实现完全一致；
- **文件锁覆盖窗口精确**：只要本进程有一个线程在临界区内，文件锁就被持有；跨线程误释放不可能发生；
- **无新增死锁**：线程等待其它进程释放文件锁时持有 gate，与旧实现 `sem_wait` 阻塞等价；锁获取顺序 gate → opMutex → 内核单向，不成环；
- **同进程多实例同 key**（如同一命名事件被 Open 两次得到两个 C++ 对象）：注册表按锁文件路径合并，映射到同一份 gate 状态——与旧 XSI"同 key 同信号量集"行为一致；
- **崩溃安全不受影响**：gate 是进程内存，随进程消失；文件锁由内核释放。

## 3. Review 结论：与原实现的功能对照

对调用点逐项核对（`sysobjs.cpp` 全部使用点、`sharedmem.cpp`、`hook.cpp`、`platform/ios/atoms.mm`）：

| 项目 | 结论 |
|---|---|
| 公开接口（`ISemRwLock` 四方法、`init` 签名、`getKey`） | **不变**，所有调用点零改动 |
| 排他锁语义（全局句柄表、GlobalMutex 全部实际路径） | **不变** |
| 进程内线程互斥 | **不变**（依赖 2.3 的 gate 层；纯文件锁版本曾缺失，本次 review 已补） |
| 同进程多实例同 key/同名 | **不变**（gate 状态按锁文件路径合并） |
| `lockShared` 跨进程行为 | **增强**：原 XSI 版 slot0 计数=1，读者实际也被串行化；新版跨进程读者可真并发。已核对全部三处读临界区（`WaitForSingleObject`/`WaitForMultipleObjects` 取 fd、`GetObjectName` 拷贝名字）均为只读，并发安全 |
| 崩溃残留 | **根治**：信号量残留 → 内核自动释放，不可能 wedge 下次启动 |
| init 重置副作用 | **消除**：原 XSI 版每个进程 init 都 `SETVAL=1`，可能破坏他进程持有的锁；文件锁无此问题 |
| `SharedMemory` 析构 | 仅去掉 `sem_unlink`；刻意不 unlink 锁文件（见 2.1），`shm_unlink` 行为不变 |
| Android/OHOS/iOS 分支 | `TSemRwLock` 统一为单类，移动端改走进程内匿名锁（不再 `open` 命名锁文件）、桌面端保留 fcntl；顺带修复 Android 分支不做名字净化导致 open 失败的隐患 |

### Review 中发现并处理的问题

1. **进程内互斥缺失（已修复，见 2.3）**：纯文件锁版本在多线程下对同一命名对象失去互斥，属于功能变化，已通过 FlockGateState 层补齐。
2. **既有隐患（记录在案，不在本次范围）**：
   - `NamedWaitbleObj/FileMapObject` 的 `mutex.init(...)` 返回值未检查（原 XSI 版同样不检查）。桌面端若锁文件 `open` 失败（如目录不可写），该对象的互斥会退化为"每次 perror 但继续"。移动端锁已改为匿名实现，不再依赖 `/data/local/tmp` 可写（`SharedMemory` 的共享内存临时文件回退仍会尝试该目录）。
   - `sysobjs.cpp` 的 `kFifoRoot = "/tmp"`（命名对象 FIFO）与 `shm_open`（依赖 `/dev/shm`）仍为桌面 POSIX 路径，鸿蒙沙箱的可用性未验证，属鸿蒙深度适配的后续项。

## 4. 收益总结

1. **根治"异常退出后起不来"**：fcntl 锁内核自动释放，任何崩溃形态（SIGKILL、段错误、断言）都不残留锁状态——这是本次改造的核心动机。
2. **消灭 init 竞态副作用**：不再有"第二个进程 init 重置计数破坏第一个进程持锁"的窗口。
3. **真读并发**：跨进程读锁（`F_RDLCK`）可并发，`WaitForSingleObject` 等读路径在多进程场景下吞吐更好。
4. **跨平台统一**：Android/OHOS/Linux/macOS 四端共用一份实现，平台差异收敛为 `lockDir()` 一处；Android 分支的名字净化隐患一并修复。
5. **零调用点改动**：类名、接口、`init` 签名、模板参数全部保留，Windows 真Win32路径不受影响。

## 5. 约束与注意事项

- **锁不可重入、不可嵌套**：每段临界区一次 lock 配一次 unlock（与原信号量一致）。
- **锁文件不可 unlink**（理由见 2.1）；清理只需在程序外删除 `/tmp/soui_flock_*` / `/data/local/tmp/soui_flock_*`，随时安全。
- **移动端目录前提**：移动端锁已改为进程内匿名实现，全局句柄表初始化（`getRwLock`）不再依赖任何目录可写；但 `SharedMemory` 的共享内存仍会先尝试 `ASharedMemory`/临时文件（`/data/local/tmp/soui_shm_*`），失败则回退堆内存，因此全局句柄表在移动端恒可成功初始化。
- **全局构造期可用**：整套机制（锁文件 open、gate 注册表）不依赖任何运行时注入的平台 API，可在 `main()` 之前的静态构造中安全使用。

## 6. 回归测试

`demos/fun_test/test_flock.cpp`（套件 `swinx_flock`，非 Windows 编译），直接驱动 swinx 真实锁类：

1. **`crash_holder_releases_flock`**：fork 持锁进程 → 裸 `fcntl` 验证外部进程确被拒绝 → `SIGKILL` → 验证内核自动释放 → 新进程经锁类无阻塞重取；
2. **`named_objects_usable_after_abrupt_exit`**：子进程创建命名事件/互斥后猝死 → 新进程重开对象并完成 Set/Wait 往返；
3. **`startup_survives_crashed_lock_holder` + `startup_probe`**：完整复现原故障场景——持全局句柄表锁的进程被 SIGKILL 后，`CreateProcessA` 启动全新进程重跑静态构造期（当年卡死点），必须正常启动。

所有阻塞点挂在 `SIGALRM` 看门狗下：若实现回归为可残留的锁，用例判**失败**而非挂死。子进程结果走管道传递（swinx 的 SIGCHLD 排水线程会 `waitpid(-1)` 抢收，waitpid 退出码不可靠）。

验证状态：Linux、macOS 全部用例通过。
