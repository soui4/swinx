### 1.1 分层结构

```
        SOUI4（UI 框架，不感知平台差异）
   ─────────────────────────────────────────
        swinx 公共 API 面   include/*.h（45 个 Win32 头 + GL/2 个）
   ─────────────────────────────────────────
        核心模拟层          src/*.cpp（窗口/消息、GDI 门面、内核对象、
                           文件、字符串、注册表、COM/OLE、ACC、WGL…）
   ─────────────────────────────────────────
   平台适配层   platform/{linux, cocoa, ios, mobile}
   渲染后端层   gdi/{cairo, apple}
   ─────────────────────────────────────────
        vendor 第三方       thirdparty/（20 个组件，静态编入）
   ─────────────────────────────────────────
        OS：XCB / Cocoa·CoreGraphics / UIKit / Android NDK·OHOS NDK
        （可选旁路：GLX / NSOpenGLContext，仅应用显式使用 realwnd 时参与）
```

平台差异与渲染差异被拆成**两个正交维度**：`platform/*` 负责事件循环、窗口壳、剪贴板、
输入法、键盘布局、拖放、DPI，`gdi/*` 只负责绘制。Linux 与 Android/OHOS 复用同一渲染后端
而平台层不同，macOS 与 iOS 反之——维度正交使"新增一个平台"与"新增一个渲染后端"互不牵连。
本周期新增的 OpenGL 通道刻意**不加入这两个维度**：它不是"swinx 的第三种渲染后端"（swinx 自己
不用它画任何东西），而是"把窗口句柄转成 GL 上下文"的**句柄级服务**，走 `wgl.cpp` 单文件 +
各平台一个桥（3.2 末段）。

## 二、总体评价

**结论：这是一个难度很高、完成度很高的 Win32 兼容层，且本周期把"图形"这条最硬的边界向外推了一步。**
它要解决的不是"把某个 API 翻译过去"，而是三类互相纠缠的问题——**Win32 的隐式语义**（消息派发的
锁语义、伪句柄、ANSI/Unicode 双轨、GDI 对象生命周期、**子窗口裁剪**）、**渲染模型的映射**
（GDI 的 DC/ROP/区域 → cairo 或 CoreGraphics，**DC → GL 上下文**）、以及**平台服务的桥接**
（XCB/Cocoa/UIKit/NDK 的事件与窗口模型 → HWND 消息循环，**原生视图 → GL drawable**）。
16.8 万行的自研与派生代码（不含 vendor 的 `thirdparty/`）、覆盖 5 个平台 2 个渲染后端外加一条
OpenGL 旁路、且下游有真实的重型消费者（SOUI4 及其 20+ 示例）在跑，这已经不是"玩具兼容层"的量级。

本基线值得记录的三点：

1. **新增能力落在"最不像 Win32 能抽象"的地方，且抽象方式是对的。** OpenGL 的跨平台难点不在
   `gl*` 函数（那是 Khronos 统一的），而在**上下文与窗口表面的绑定**——WGL 的 `HGLRC`/`HDC`
   在 GLX 是 `GLXContext + X drawable`、在 AppKit 是 `NSOpenGLContext + NSView`，两边的
   "share group 只能在创建时指定""一个视图同时只能挂一个 drawable"这类约束并不对应。
   swinx 的解法是把 8 个平台函数（创建/销毁/绑定/解绑/交换/入口解析/交换间隔/版本能力查询）
   收在一层，其余全部是公共逻辑，并把**上下文创建延迟到首次 `wglMakeCurrent`**——这是让
   `wglShareLists`（Win32 允许创建后再共享）在 GLX/NSOpenGL 上成立的必要条件。这类"用生命周期
   顺序去弥合语义差"的处理，是本次适配里最有含量的部分。
2. **本周期修掉的缺陷集中在"平台适配层看不见的规则"，而不是崩溃。** 三处典型：非客户区滚动条
   被 app 的合法 `WM_PRINT` 处理器整条吃掉（Linux/macOS 从未画出一条滚动条，Windows 因不编译
   swinx 而从未暴露）；子窗口可以压住父窗口滚动条（X11/AppKit 没有"客户区"概念，规则本身缺失）；
   `CharToOemBuffA/W` 用**输入长度**当输出缓冲长度（多字节输出会越界）。这些都属于"跨平台正确性"
   而非"功能缺失"，也解释了一个现象：**swinx 的缺陷分布与平台层强相关，而不是与 API 数量强相关**。
3. **验证体系从"有门禁"走向"门禁本身也会漂移"。** 09-19 版把 325 条用例注册成 CTest 门禁；
   本周期又加了 API 面门禁（`api_scan.py --check` 进 PR）。但这条新门禁在接手时是红的——OpenGL
   加了 24 个入口却没刷新 `api_scan.json`。**这是本版最值得记的一条**：门禁的存在不等于门禁在跑、
   更不等于被理解；一个"忘记重生成派生文件"就能让它变红的门禁，其价值取决于发布流程是否把它当回事
   （本版已修复，见 6.4）。

综合评分（满分 5 分）：

- **架构设计 ★★★★☆**：平台/渲染二维正交、公共 API 面严格等于 Windows SDK、下游零感知——三点
  仍成立，且 OpenGL 通道的接入没有破坏它们（GL 头 `wgl.h` / `GL/gl.h` 与 Windows SDK 同名同结构）。
  扣分在 `src/` 内 Wine 派生文件与自研代码风格混编（3.4），以及 `src/wgl.cpp` 用 `#ifdef __APPLE__`
  做平台分叉（同文件内两个平台实现，而不是落到 `platform/*`）——这是为"GL 只是旁路服务"做的取舍，
  但与 3.2 声称的"实现下沉"纪律不完全一致。
- **可靠性 ★★★★☆**：核心路径有 425 条 CI 门禁用例（三平台）+ 构建即测试 + valgrind 抑制基线；
  本周期修掉的滚动条、子窗口裁剪、`CharToOemBuff*` 越界都是真缺陷。扣分在：36 项实质空实现里仍有
  5 项真实功能缺口（4.3 类别三）、集成测试仍以人工为主、**OpenGL 能力没有任何自动化验证**
  （`opengl_demo` 只在 tag 构建里编译，PR 门禁不覆盖，见风险 11）。
- **工程规范 ★★★★☆**：文档体系完整且与代码同步（17 篇，本周期新增 5 篇，其中 OpenGL 一份 684 行
  可直接当实现说明用）、许可清单中英双份。CI 由三条工作流扩到**四条**（新增 API 面门禁），本项原
  扣分点进一步消除；余下扣分在**文档声称的门禁脚本不存在**（第八章风险 12）与**许可表两行行数已漂**（7.1）。
- **可维护性 ★★★★☆**：分层清晰、API 清单可机械化重生成（含 `--check` 模式）。扣分在派生数据
  （`api_scan.json` / `清单.md`）需人工记得重生成，以及单作者（bus factor = 1）。
- **测试保障 ★★★★☆**：427 个用例、425 条进门禁（较上版 +100 例 / +100 条），跨平台同源用例，

## 三、架构与实现现状

### 3.1 公共 API 面严格等于 Windows SDK

`include/` 下 45 个顶层头文件与 Windows SDK 同名同结构：`windows.h` 聚合 `winuser.h`、`gdi.h`、
`sysapi.h`、`class.h`、`commctrl.h`、`unknwn.h`、`oaidl.h`、`oleacc.h`、`shlwapi.h` 等。

这条纪律的价值在于**下游零修改**：SOUI4 的代码直接 `#include <windows.h>`，不需要
`#ifdef` 分支。目录里没有 `swinx_*.h` 之类的扩展头；平台桥需要的内部助手
（如 ACC 的 `SwinxAccResolvePath`、OpenGL 的 `swinxGLCreate`/`swinxGLMakeCurrent`）都放在
`src/` 下或由 `wgl.cpp` 自己 `extern` 声明，明确**不对外导出**。

本周期对这条纪律是一次**真正的考验**：新增的 OpenGL 面如果按"加个 `swinx_gl.h`"来做，就会在公共
API 面开一个口子。实际做法是 `include/wgl.h` + `include/GL/wglext.h` 完全按 Windows SDK 的同名
头组织（`wgl.h` 的 23 个入口与 `wingdi.h` 中 WGL 段的签名一致，`GL/gl.h` 只做"转发平台 GL 头 +
引入 `<wgl.h>`"，使 `wgl*` 的声明**只有一处**）。扩展入口（`wglCreateContextAttribsARB` 等）按
Windows 的惯例由 `wglGetProcAddress` 运行期取，头里只给 `PFN*` 类型与常量——即"SDK 里有什么就
声明什么，SDK 里没有的不进头"。

### 3.2 五平台 × 两后端的实际编译归属

由各 `*.cmake` 的实际源文件清单与源码 `#if` 分支核定（非文档声明）：

| 目标平台 | 平台适配层 | 渲染后端 | 构建脚本 | 平台专有依赖 |
|---|---|---|---|---|
| Linux（桌面） | `platform/linux` | `gdi/cairo` | `linux.cmake` | ALSA（可选）、**libGL/libX11（`dlopen`，可选）** |
| macOS | `platform/cocoa` | `gdi/apple` | `macos.cmake` | Cocoa / CoreGraphics / CoreServices / **OpenGL.framework** |
| iOS | `platform/ios` | `gdi/apple` | `ios.cmake` | UIKit |
| Android | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | Android NDK |
| OpenHarmony | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | OHOS NDK（`ace_napi`/`ace_ndk`/`native_window`/`hilog`） |

平台差异的收敛方式目前有**四种形态**，本周期各有一处新例证：

1. **实现下沉**：`src/platform/<平台>/` 提供该平台实现，`src/*.cpp` 只写 Win32 语义。
   本周期所有平台相关修复（滚动条、裁剪、IME、文件锁）都落在这个位置。
2. **同一符号、分目录实现、链接期解析**：公共助手声明集中在 `src/SwinxUtils.h`（当前为
   `swinx_messageBeep`），各平台目录给出同名同签名实现，`file(GLOB)` 只把当前平台的源文件放进
   构建。暂不实现的能力在 `platform/mobile/utils.cpp` 保留占位定义（返回 `FALSE`），以维持这一
   形态而不是退回 `#ifdef`；移动端需要平台能力时转发 `g_platformAPI`（`include/platform_api.h`，
   **本周期由 v3 升至 v4**：新增 `shell.shellExecute`，与既有的 `audio.messageBeep`、
   `ime.showSoftKeyboard`、`path.getSpecialFolderPathA` 同路），由宿主应用层补足差异。
3. **把"平台能力的差异"抽象成句柄族**（09-19 引入）：键盘布局三函数在四组适配器上语义差别很大
   （Linux XKB group / macOS TIS / iOS 与移动端只有唯一布局），swinx 让顶层入口保持 Win32 的 HKL
   语义，把差异压到各平台 `SConnection` 的三个同名方法里，`HKL` 取值约定收在 `src/hkl.h`。
4. **能力门控 + 延迟创建**（本周期新增，OpenGL 专用）：`wgl.cpp` 定义 8 个平台函数
   （`swinxGLCreate` / `Destroy` / `MakeCurrent` / `ClearCurrent` / `Swap` / `GetProcAddress` /
   `SetSwapInterval` / `PlatformSupportsContextAttribs`），macOS 侧转调 `SGLBridge.mm`（对外 7 个
   `extern "C"`），Linux 侧在同一文件内联 GLX。这里没有沿用形态 2 的"分目录同名实现"，原因是
   **依赖不能落地**：Linux 侧不引入 X11/GLX 开发头与链接期依赖，全部经 `dlopen` + `dlsym` 运行期
   解析（缺库时返回失败），macOS 侧则直接链接 OpenGL.framework。同一份公共层（上下文对象、核心
   入口、扩展分派表）在两平台共用，两个 `#ifdef` 分支只出现在文件首尾。

**OpenGL 桥的三个关键设计**（细节见《swinx-OpenGL(WGL)跨平台实现》，本报告只记结论）：

- **上下文延迟到首次 `wglMakeCurrent` 才创建**。GLX 与 NSOpenGL 都只允许在创建时指定 share
  group，而 Win32 的 `wglShareLists` 允许创建之后共享；延迟创建是让这条 Win32 语义成立的必要条件
  （`wglCreateContextAttribsARB` 例外，它当次就要拿到可用上下文）。
- **Linux 侧 FBConfig 必须与窗口 Visual 一致**。窗口创建时记下的 `_Window::visualId` 用来挑同
  Visual 的 FBConfig，挑不到（该 Visual 不支持 GLX）则明确失败——否则 `glXMakeCurrent` 会**静默**
  失败，表现为"程序在跑、画面全黑"。
- **macOS 侧一视图只能挂一个 drawable**，临时上下文 `setView:` 同一视图会顶掉前一个，而旧上下文的
  `view` 指针仍指回该视图（`ctx.view != view` 这种判断查不出来）⇒ 销毁临时上下文时 `clearDrawable`
  会把主上下文变成永久黑屏。解法是按视图记**绑定栈**（`SwinxBindView` / `SwinxUnbindView`）：
  创建不绑、`makeCurrent` 抢占、销毁后重绑栈顶。

### 3.3 第三方全 vendor 化

`thirdparty/` 内置 20 个组件（cairo、pixman、fontconfig、freetype、libpng、zlib、brotli、
expat、libxcb、xcb-util 家族、xcb-imdkit、xkbcommon、dbus-1.14.10 等），全部由顶层
`add_subdirectory(thirdparty)` 静态编入；本周期文件数 7,843 未变。

收益是**构建可复现与零版本风险**：目标机不需要预装任何图形/输入/无障碍库，也不存在
"发行版 cairo 版本不同导致行为漂移"。代价是 `thirdparty/` 下约 7,800 个文件进入仓库
（占仓库受版本管理文件数的 96.5%）。此外 vendored 库的**实际头文件即为契约**——文档已记录
"以 vendored 库的实际行为为准，而非上游文档"这一纪律。

**OpenGL 是这条纪律的唯一例外，且理由充分**：GL/GLX 不是普通库，它同时绑着驱动（`libGL`）与
显示服务器（`libX11`）的版本矩阵，把它 vendor 进来既无必要也不可能正确处理驱动侧。swinx 的选择是
**不入 vendor、不链开发头、运行期 `dlopen`**：`libGL` 缺失 ⇒ GL 入口全部返回失败，其余功能不受影响。
代价是编译期没有类型检查（GLX 的类型与常量在 `wgl.cpp` 里自建了一份最小声明），收益是把"依赖
OpenGL"从构建期约束降级为运行期可选。

### 3.4 遗留与自研代码的边界

代码来源可分为两段：`src/` 与 `include/` 内一批文件源自 Wine 的对应实现
（`include/winerror.h`、`cursoricon.cpp`、`safearray.cpp`、`profile.cpp`、
`malloc_impl.cpp`、`cmnctl32/listbox.cpp`、`uitools.cpp`、`list.h`、`cmnctl32/heap.h`，
共 9 个文件），其余为自研。Wine 派生部分继承了 Wine 的调试宏风格（`FIXME`/`TRACE`）
与 GNU 扩展写法（大量 `__attribute__((unused))`），与自研部分的风格并不统一。
这批文件的著作权与许可状况已在 `license_CN.txt` / `license_EN.txt` 中逐项披露，见 7.1。

### 4.5 接口面缺口（不在 4.3 / 4.4 口径内的另一类空白）

4.3 统计"空实现"、4.4 统计"仅声明未定义"，两者衡量的都是**声明与实现是否成对**。但还有一类

**为什么第二、三行是"静默失败"**：`WC_EDITA` 这类**类名只是宏**，调用方引用的是
`CreateWindowEx` 这个**已定义**的函数，因此编译与链接都会通过，直到运行时才发现窗口类不存在。
**这是 swinx 目前唯一一类"静默失败"面，排查成本高于链接期报错**——若调用方不检查
`CreateWindowEx` 的返回值，现象是"程序起来了、界面是空的"。

**结论**：swinx 的完备度仍是"**承载用 SOUI 编写的应用**"这一目标下的完备度，**尚未达到
"让既有 Win32 程序零成本迁移到多平台"**。二者相差"原生控件库 + 窗口菜单栏 + 资源对话框"三块。
该目标在能力上可达——`ListBox` 已证明 Wine 控件可整体搬运，消息 / DC / GDI / 类注册这套地基
稳固；差距属**工作量而非架构不确定性**。本周期新增的 OpenGL 通道不改变这个判断：它服务的是
"SOUI 应用里嵌一块 GL 视图"，而不是"让任意 Win32 程序里的 GL 代码跑起来"（后者还缺 `SetPixelFormat`
的真实多格式支持与 `ChoosePixelFormat` 的格式协商）。

## 五、无障碍（ACC）实现现状

ACC 是本版本（1.5）明确列入交付口径的能力，实现已完整可查；**本周期 ACC 六个文件零改动**
（`SAtSpi.cpp` 2,727、`SNsAccessibility.mm` 847、`oleacc.cpp` 768、`safearray.cpp` 1,696、
`objbase.cpp` 302、`variant.cpp` 133，行数与上一版逐行一致），故本章为**复核而非重写**。

### 5.1 三层结构

```
   系统 AT（Windows Narrator / macOS VoiceOver / Linux Orca·accerciser）
        │
        ▼  平台无障碍协议：MSAA(COM) / NSAccessibility / AT-SPI2(D-Bus)
   平台桥   swinx：Windows 原生 oleacc ｜ cocoa:SNsAccessibility ｜ linux:SAtSpi
        │
        ▼  WM_GETOBJECT / LresultFromObject / ObjectFromLresult
   SOUI 侧  SHostWnd::OnGetObject → SAccessible（唯一 MSAA 门面）
        │
        ▼  IAccProxy（纯 SOUI 语义，不继承 IAccessible）
   控件      SWindow / SButton / SListView / STabCtrl …
```

关键约束：**swinx 不持有 `IAccessible`**。`WM_GETOBJECT` 往返由一张弱登记句柄表
（容量 256、FIFO 淘汰、**不 AddRef**）承接，客户端按 `(句柄, wParam)` 匹配解析；
`AccessibleObjectFromWindow` 把 OBJID 按 32 位有符号数放进 `LPARAM`（复刻真实 oleacc 的
符号扩展），`NotifyWinEvent` 在**事件产生时**对钩子做快照、无匹配即丢弃，投递由消息泵异步完成。

### 5.2 三平台的接入方式

| 平台 | MSAA API 提供方 | 桥文件 | 下层协议 | 桥是否持有对象 |
|---|---|---|---|---|
| Windows | 系统 `oleacc.dll` / `oleaut32.dll` | 无（原生） | MSAA/COM | 不适用 |
| macOS | swinx `oleacc.cpp` + `objbase.cpp` + `variant.cpp` | `platform/cocoa/SNsAccessibility.mm` | `NSAccessibility` | 不持有（身份壳） |
| Linux | 同左 | `platform/linux/SAtSpi.cpp` | `AT-SPI2` over D-Bus | 不持有（确定性路径编码） |

两个桥的共同策略是**不做对象缓存**：Linux 桥把对象路径按
`/org/a11y/atspi/accessible/w<hwnd>_c_<i>_<j>` **确定性编码**，每次请求按路径从窗口根重新
导航一遍（O(深度) 次调用），换来"绝不访问已销毁控件的悬垂指针"；macOS 桥用不持 COM 的
身份壳 + 缓存。共享的路径下钻内核是 `SwinxAccResolvePath`（`oleacc.cpp`），两平台复用。

### 5.3 非 MSVC 工具链上的 COM 实现

gcc/clang 不支持 `__uuidof` 关键词，也不提供 COM 运行时。swinx 用四件事补齐：

| 补齐项 | 位置 | 机制 |
|---|---|---|
| 接口声明宏 | `include/basetyps.h` | `DECLARE_INTERFACE_`/`STDMETHOD`/`THIS_`/`PURE` 的 C 与 C++ 两套展开 |
| IID 获取 | `include/guiddef.h` | `__uuidof(X)` 与 `__suidof(X)` **都定义为 `X::GetIID()`**；配合 `DECLARE_CLASS_SIID` 在每个接口内生成静态函数——把编译期类型→IID 映射降级为普通静态函数调用 |
| 引用计数与 QI | `src/SUnkImpl.h` | `IUNKNOWN_BEGIN/ADD_IID/END` 宏展开出 `AddRef`/`Release`/`QueryInterface`；`SUnkImpl<T>` 模板提供 `m_cRef` 与 `OnFinalRelease`（`delete this`） |
| GUID 比较与定义 | `include/guiddef.h` | `IsEqualIID` = `memcmp`；`DEFINE_GUID` 以 `__attribute__((weak))` 弱符号定义，避免多编译单元重复定义链接冲突 |

`BSTR`/`VARIANT`/`SAFEARRAY`/`IDispatch` 由 swinx 自行提供（`bstr_internal.h`、
`variant.cpp`、`safearray.cpp`），`IUnknown` 由 `include/unknwn.h` 声明。
这四者齐备后，SOUI 的 ACC 代码可一字不改地跨三平台编译。

### 5.4 覆盖边界（可用于判断"某控件在某个平台上读得到什么"）

- **MSAA 服务端**（`oleacc.cpp`）已实现 15 个入口：`LresultFromObject`、`ObjectFromLresult`、
  `AccessibleObjectFromWindow`、`AccessibleObjectFromPoint`、`AccessibleObjectFromEvent`、
  `AccessibleChildren`、`NotifyWinEvent`、`SetWinEventHook`、`UnhookWinEvent`、
  `GetRoleText{A,W}`、`GetStateText{A,W}`、`SwinxDispatchPendingWinEvents`、`SwinxAccResolvePath`。
  **注意 `AccessibleObjectFromPoint` 属已实现之列**，不应按"未提供"处理。
- **Linux 桥暴露的 AT-SPI2 接口（8 个）**：`Accessible`、`Action`、`Application`、`Cache`、
  `Component`、`Event`、`Registry`、`Socket`。
  **未暴露**：`Text`、`EditableText`、`Value`、`Selection`、`Table`、`TableCell`、
  `Hypertext`、`Document`、`Image`、`Collection` 等。影响：Orca 等客户端能看到**对象树、
  角色、名称、状态、事件**，但**读不到文本内容、进度值、选区与表格结构**。
- **macOS 桥暴露的 NSAccessibility 成员（15 个）**：`children`、`enabled`、`focused`、
  `frame`、`frameInParentSpace`、`help`、`hidden`、`hitTest`、`parent`、`performAction`、
  `performPress`、`role`、`roleDescription`、`title`、`value`（另实现 `isAccessibilityElement` 标志）。
  **未暴露**：`selectedChildren`、`rows`/`columns`、`minValue`/`maxValue`、
  `orientation`、`subrole`、`customActions`、`selectedTextRange` 等——与 Linux 侧的
  边界基本对应。
- **事件归因粒度**：两个桥的钩子均未使用 `idObject`，事件按 `hwnd` 归因到窗口级
  （"这个窗口有东西变了"而非"第 3 个页签变了"）。`idObject` 中携带的 SWND 是 MSAA 允许的
  custom object ID，服务端 `SHostWnd::OnGetObject` 会用 `SWindowMgr::GetWindow` 反查，
  因此**该信息可解析**（经 `AccessibleObjectFromEvent`），桥侧细化粒度属未实现路径。

### 6.2 线程安全：CountMutex

Win32 的消息派发语义要求"进入窗口过程前释放系统内部锁"。swinx 用 `CountMutex`
（`src/countmutex.h`，51 行）适配：在 `CallWindowObjProc` 与消息泵的 `WM_TIMER` 回调处
`FreeLock()` → 调用业务回调 → `RestoreLock(preLock)`，把锁深度**降到 0 再恢复到原深度**。

这不能靠 `std::recursive_mutex` 单独完成（标准设施没有"一次清空、按值恢复"），
故保留自定义类。约束已文档化：`FreeLock`/`RestoreLock` 必须**同线程配对**、
`preLock` 原样回传、不得交叉嵌套；**回调窗口期内对象处于无锁状态**是与真实 Win32 一致的
特性——新增回调窗口期调用点时必须显式意识到这一点。

### 6.3 内存与泄漏检测

- `src/malloc_impl.cpp`（461 行）提供 `IMalloc` 实现，作为 `CoGetMalloc` 的可替换分配器。
- `valgrind-linux.supp` 抑制基线：记录 valgrind 已知误报（如 glibc AVX2 `wmemcmp` 的 32 字节块
  越界读——ifunc 分派绕过 valgrind 拦截器导致的假阳性）。抑制项附带成因说明，而非静默关闭。
- **判读纪律**：① valgrind 报告需先区分"fork + `_exit` 继承的快照"与"本进程真实泄漏"——
  `test_flock.cpp` 的三个 `fork()` 子进程各自报出的 `definitely lost` 段逐字节一致，属继承堆
  快照而非泄漏，跑本工程应加 `--child-silent-after-fork=yes`；② X11 请求是**共享输出队列**，
  "未初始化字节"的报错栈顶只是最后调 `flush` 的人（cairo 常被误指），不能照栈顶归因。
- **静态生存期**：`src/sharedmem.h` 的 flock 全局登记表会被**静态析构路径**
  （`GLobalHandleTable::~` → `SharedMemory::~` → `~TSemRwLock`）访问。由于该 inline 函数的静态
  局部量由首次初始化它的 TU 注册析构，而可执行文件的 `__cxa_finalize` 恒早于动态库的
  fini_array，"exe 先销毁表、库再析构对象"的顺序不可修复 ⇒ 该表改为 **leak-on-purpose 的单例
  对象**（互斥量与表收成同一类的两个成员，按声明逆序析构），运行期行为不变，退出时多一份空表
  计入 still-reachable。
- **本周期新增：文件锁单类化**。`TSemRwLock` 现在同时承担"按 key"与"按名"两种锁
  （`init(uint32_t)` / `init(const char*)` 两个重载），桌面端以 fcntl POSIX 记录锁实现、
  移动端用匿名实现；`TNamedSemRwLock` / `TAnonymousRwLock` 两个别名已删除。动机是原先的
  XSI 信号量集与 POSIX 命名信号量**在持锁进程崩溃后计数不会恢复**，下一个进程会在同一把锁上
  永久阻塞（阻塞点还在 `main()` 之前）；fcntl 记录锁由内核在进程退出时自动释放，可根治。
  移动端另有一个实际障碍：Android / OHOS 沙箱内没有可用的 `/tmp` 作为跨进程命名目录。

## 八、风险与限制清单

按优先级排序：

1. **门禁覆盖面只到桌面三平台**。CI 现有四条工作流，其中三条（`pr-core` 的 Linux/Windows/macOS
   job 与 `build.yml` 的 7 个配置）由 `submodules: recursive` 检出 swinx 并跑 425 条门禁用例，
   **但 iOS / Android / OpenHarmony 无任何自动构建与测试**：这三端的
   回归完全依赖人工，而它们恰恰是 vendor 依赖最多、平台 API 最不标准的端（OHOS NDK、Android NDK、
   UIKit）。本周期新增的 IME、文件锁、`ShellExecute` 通路**全部落在移动端**，却没有任何自动验证。
   至少应加"交叉编译不回归"的 job。
2. **接口面缺口：迁移既有 Windows 程序所需的"原生控件 / 窗口菜单栏 / 资源对话框"未建立**（4.5）。
   内置注册的窗口类仅 `Static` / `Button` / `ListBox` 三个；`Edit` / `ComboBox` / `ScrollBar` 与
   全部公共控件无实现；窗口自己的菜单栏（`SetMenu` / `GetMenu` / `DrawMenuBar`）无声明；
   无对话框实例化 API（`DialogBoxParam` 族）。**量级远大于声明层面的缺口**，且其中"建原生控件窗口"
   是**运行期静默返回 `NULL`**。
   另有**声明层面的 5 项 API 缺口**（4.3 类别三）：`ScrollWindowEx`、`SendNotifyMessage{A,W}`、
   `SetWindowExtEx`、`SetMenuItemBitmaps`，按是否出现调用方逐个排期即可。本周期未新开也未关闭任何
   功能缺口——**新开的 11 项"空实现"全部是 OpenGL 的平台无能力降级（4.3 类别四），不是缺陷**。
3. **ACC 扩展面**（5.4）。Linux 侧缺 `Text`/`Value`/`Selection`/`Table` 等 10 余个
   AT-SPI2 接口，macOS 侧缺 `selectedChildren`/`rows`/`minValue` 等。当前 AT 客户端
   能导航对象树但读不到文本与数值内容。**属能力边界而非缺陷**，但直接决定"屏幕阅读器
   能否真正朗读应用内容"。
4. **ACC 事件归因粒度**（5.4 末条）。桥未使用 `idObject`，事件止于窗口级。可经
   `AccessibleObjectFromEvent` 解析细化，属未实现路径。
5. **参数化用例未被完整注册**（6.1）。`gtest_add_tests` 在配置期用正则扫源码，`TEST_P`
   拆不全（官方文档明说）。当前测试集未用 `TEST_P`，故暂无实际影响，但新增参数化用例时
   必须单独核验注册结果。**同源的"正则不锚行首"问题已经显形**：425 条门禁里有 3 条来自
   注释掉的 `TEST` 行，是空跑条目。
6. **HKL 低字语义与真实 Win32 不一致**。真实 Windows 的 `HKL` 低字是 `LANGID`
   （`third-part/richedit41` 就用 `LOWORD(GetKeyboardLayout(0))` 取语言 id），而 swinx 的
   HKL 是"索引 + base"的内部编码，不满足这一约定。当前仅在 `SOUI_BUILD_RICHEDIT`（默认 OFF
   且只在 Windows 暴露）下会被触达，属潜在项。
7. **macOS 跨进程 HWND IPC 空缺**。照搬"HWND 即跨进程窗口句柄"的现有设计在 macOS 上
   **不成立**（HWND 是进程内对象指针），但基于 HWND 语义实现 IPC **可行**，前提是把契约改为
   "全局窗口 ID ↔ 进程内 HWND"映射；同族进程互发消息可行、跨进程按类名/标题查找需新增注册表、
   向任意第三方应用窗口发消息不可行（且不合规）。现有 shm / 具名对象 / fd 消息泵三层设施可复用。
8. **`thirdparty/` 体量**。7,843 个文件进入版本库，占仓库受版本管理文件总数（8,126）的
   **96.5%**；对 clone 体积与检索体验有实际影响。是否接受这一取舍需明确定调（当前是接受的）。
9. **OHOS 深度适配**（延续项）：沙箱下 `/tmp`、`shm_open` 可用性待真机验证（本周期文件锁改动
   正踩在这条限制上，改为移动端匿名实现）；ACC 在 OHOS 上不启用。
10. **单作者**（bus factor = 1）。
11. **OpenGL 能力没有任何自动化验证**（本版新增）。`demos/opengl_demo` 有 `--selftest`
    （Windows 侧实测 16 PASS / 0 FAIL / 1 SKIP），但它**不在 PR 门禁的构建目标内**
    （`pr-core.yml` 只 `--target fun_test`），只有 tag 触发的 `build.yml` 全量构建才会编译到它。
    即：`wgl.cpp` 的**编译**已被 Linux/macOS 的 PR job 覆盖（它是 swinx 库的一部分），但
    **运行**没有任何覆盖——三段上下文创建/绑定逻辑、GLX FBConfig 阶梯、macOS 视图绑定栈，
    全部靠人工在真机上看。
12. **文档声称的静态门禁脚本不存在**（本版新发现）。《swinx-非客户区绘制与 WM_PRINT 分发缺陷》
    第 170 行把 `tools/check_ncpaint_direct.py` 列为"本条修复的静态门禁（5 条断言 + 4 项变异）"，
    但 `swinx/tools/` 下只有 `gen_cptable.py`，该脚本在仓库历史中从未出现（`git log --all` 无记录）。
    同类的 `check_macos_shape.py` / `check_ios_shape.py` 亦无。**文档与门禁设施漂移的后果比缺门禁更糟**：
    读者会以为这条修复被机器守着。
13. **扫描器分级的可信边界**（本版新发现）。`api_scan.py` 的 stub 判据是"无外部调用且函数体 ≤ 4 行"，
    对"直接返回全局状态的 getter"必然误判（`wglGetCurrentContext` 即本周期实例）。37 项空实现里

## 九、建议路线图（按性价比排序）

1. **给移动端与 OHOS 加"交叉编译不回归"CI job**（关闭风险 1）。Android NDK 与 OHOS NDK 的
   交叉编译可在 Linux runner 上完成，成本远低于真机测试；先把"能编过"这条底线自动化，
   就等于把三端的构建回归纳入门禁。本周期移动端的改动（IME、文件锁、`ShellExecute`）恰恰证明
   这块最需要机器盯着。
2. **把 API 门禁从"同步检查"升级为"回退检查"**（关闭风险 13 的一半）。
   `api_scan.py --check` 现已接入 PR，但只比对总数与名单；建议让它**逐函数比对 `agg`**，
   对 `impl → stub` 直接失败。已有基础设施为零成本扩展，且能挡住"改实现不改声明"这类最隐蔽的回退。

## 十、结论

swinx 1.6 用约 **16.8 万行**自研与派生代码（`src/` + `include/`，不含 vendor 的 `thirdparty/`）
完成了两件事：把 Win32 API 语义搬上 5 个平台 2 个渲染后端，并让这套语义在真实的重型消费者
（SOUI4 及 20+ 示例工程）面前站得住。架构上的两条主线——**公共 API 面严格等于 Windows SDK**
（下游零 `#ifdef`）与**平台/渲染二维正交**（新增平台与新增后端互不牵连）——是本项目最重要的
设计资产。本周期这条资产经受了一次新考验：**OpenGL 这样的"窗口表面绑定"问题被塞进同一个模子
而没有破坏它**——`wgl.h` / `GL/gl.h` 与 SDK 同名同结构，GL 通道作为"句柄级服务"旁挂在两个
正交维度之外，`SGLBridge.mm` 与 `wgl.cpp` 的 GLX 分支各管一端。

本基线的实质进展有两条主线。**其一是图形能力**：OpenGL/WGL 兼容层（约 1,720 行）让 SOUI 的
原生子窗口能在三端跑 GL，API 面因此从 1,042/913 涨到 **1,066/937**（完整实现 894、部分 6、
空实现 37、仅保留声明 129、实际未提供 123）；配合上下文延迟创建、FBConfig 按 Visual 匹配、
macOS 视图绑定栈这几处设计，把 GLX/NSOpenGL 与 WGL 的语义差填平了。**其二是跨平台正确性**：
非客户区滚动条、子窗口客户区裁剪、`CharToOemBuff*` 越界、移动端文件锁与 GBK 兜底——这五处
都属于"Windows 侧永远看不见、移动端与桌面 Linux/macOS 才显形"的规则层缺陷，是兼容层最难靠
review 发现的一类。**测试侧**，门禁从 325 条扩到 **425 条**（427 个用例、36 个文件），
并新增了 API 面门禁。

技术侧的待办边界依然清楚：**声明层面的 API 缺口仍是 5 项待排期 + 1 项已澄清**、
129 项"保声明不给符号"的集合两个月未变；**接口面层面仍缺"原生控件库 / 窗口菜单栏 /
资源对话框"三块**（4.5）——它决定"既有 Windows 程序能否零成本迁入"，**当前答案仍是还不能**。
而本版新增的三条判断值得单独强调：其一，**门禁本身也会漂移**——API 门禁在接手时是红的，
说明"派生数据重生成"这一步还没被流程固化；其二，**指标会骗人**——37 项"空实现"里有 1 项是
扫描器对 getter 的误判，趋势必须人工复核才能用；其三，**文档会替不存在的设施作证**——
`check_ncpaint_direct.py` 被写进文档却从未存在，这类"虚假的安全感"比缺门禁更贵。

**本版最需要补的一块，仍是门禁的覆盖面**——425 条门禁只覆盖桌面三平台，iOS / Android / OHOS
仍无任何自动回归，而本周期移动端的改动量恰恰最大；紧随其后的是"OpenGL 能力零运行期验证"。
两者都属于流程与自动化成本，不是不确定性问题。
