## 一、项目概况

| 维度 | 数据 |
|---|---|
| 定位 | Win32 API 兼容层，让为 Windows 编写的 UI 框架（主要为 SOUI4）直接运行于 Linux / macOS / iOS / Android / OpenHarmony |
| 版本 | `version.txt`：1.0（2025/5/3 框架搭建）→ **1.5（2026/9/13）**，里程碑口径为"完成移动端支持、完成 IAccessible 接口跨平台、完成内存泄漏检测、线程安全检测" |
| 代码规模 | 源码（`.cpp/.mm/.c`）**80,135 行**；`src/` 内部头 **48,313 行**；`include/` 公共 Win32 头 **34,315 行**（44 个头文件）；**合计 162,763 行** |
| 平台后端 | 5 个目标平台、4 组平台适配器：`platform/linux`（桌面 Linux）、`platform/cocoa` + `platform/ios`（Apple 系）、`platform/mobile`（Android 与 OHOS 共用） |
| 渲染后端 | 2 个：`gdi/cairo`（Linux、Android、OHOS）、`gdi/apple`（macOS、iOS） |
| API 面 | 头文件声明 **1,042** 个函数；有符号定义 **913**（完整实现 884 / 部分实现 6 / 空实现或语义桩 23）；仅保留声明 **129**（其中 6 项为扫描器误收录的宏，**实际未提供 123 项**） |
| 测试 | `demos/fun_test`：**31 个 `test_*.cpp` + 327 个 gtest 用例**。其中 **325 条 headless 用例已登记为 CTest 门禁**（`soui-unit` 323 / `soui-integration` 1 / `soui-e2e` 1），另有可选的 `soui-gui` 1 条与 `soui-interactive` 2 条默认不进门禁；Linux/macOS 桌面构建下仍保留"编译完成即自动运行"（`POST_BUILD`） |
| 第三方依赖 | 全部 vendor 化：`thirdparty/` 内置 cairo、fontconfig、freetype、pixman、libpng、zlib、brotli、expat、libxcb、xcb-util 家族、xcb-imdkit、xkbcommon、dbus-1.14.10 等 **20 个组件**（7,843 个受版本管理文件，占仓库文件总数 8,111 的 **96.7%**）；构建期唯一可选的系统依赖是 ALSA（缺失时降级到外部播放器） |
| 文档 | `doc/` 下 **15 篇**：ACC 桥实现流程、ACC 架构、跨平台 ACC 总结、Linux AT-SPI 桥接、macOS HWND 跨进程 IPC 可行性调研、API 实现清单、跨平台内核对象、文件锁、资源编译、CountMutex 设计说明、历次总体评估报告等 |
| 下游消费者 | `demos/` 下 20+ 个示例工程（含 `android-demo`、`ohos-demo`、`uieditor`）与 `games/` |

### 1.1 分层结构

```
        SOUI4（UI 框架，不感知平台差异）
   ─────────────────────────────────────────
        swinx 公共 API 面   include/*.h（44 个 Win32 头）
   ─────────────────────────────────────────
        核心模拟层          src/*.cpp（窗口/消息、GDI 门面、内核对象、
                           文件、字符串、注册表、COM/OLE、ACC…）
   ─────────────────────────────────────────
   平台适配层   platform/{linux, cocoa, ios, mobile}
   渲染后端层   gdi/{cairo, apple}
   ─────────────────────────────────────────
        vendor 第三方       thirdparty/（20 个组件，静态编入）
   ─────────────────────────────────────────
        OS：XCB / Cocoa·CoreGraphics / UIKit / Android NDK·OHOS NDK
```

平台差异与渲染差异被拆成**两个正交维度**：`platform/*` 负责事件循环、窗口壳、剪贴板、
输入法、键盘布局、拖放、DPI，`gdi/*` 只负责绘制。Linux 与 Android/OHOS 复用同一渲染后端
而平台层不同，macOS 与 iOS 反之——维度正交使"新增一个平台"与"新增一个渲染后端"互不牵连。

## 二、总体评价

**结论：这是一个难度很高、完成度很高的 Win32 兼容层。** 它要解决的不是"把某个 API 翻译过去"，
而是三类互相纠缠的问题——**Win32 的隐式语义**（消息派发的锁语义、伪句柄、ANSI/Unicode 双轨、
GDI 对象生命周期）、**渲染模型的映射**（GDI 的 DC/ROP/区域 → cairo 或 CoreGraphics）、
以及**平台服务的桥接**（XCB/Cocoa/UIKit/NDK 的事件与窗口模型 → HWND 消息循环）。
16 万行量级的自研 + vendor 代码、覆盖 5 个平台 2 个渲染后端、且下游有真实的重型消费者
（SOUI4 及其 20+ 示例）在跑，这已经不是"玩具兼容层"的量级。

本基线值得记录的三点：

1. **API 覆盖面继续可量化，且实现面未回退。** `doc/swinx-API实现清单.md` 与 `doc/tools/api_scan.py`
   让"swinx 到底支持多少 Win32"从印象变成数字：**913/1,042 个声明有定义**，其中 884 个为完整
   实现、6 个部分实现、23 个空实现或语义桩；129 个仅有声明（扣掉 6 项宏，实际未提供 123 项）。
   本周期把键盘布局族 3 项、`DragFinish` 1 项、`AdjustWindowRectEx` 1 项从"空实现"转成"完整
   实现"，把 BSTR 换长族 2 项从"仅声明"转成"完整实现"——**净增 7 项实现、减少 7 项空白**。
2. **测试从"构建的一部分"变成"CI 门禁的一部分"。** 这是本版最实质的变化。此前 `fun_test` 只有
   "编译完自动跑一遍"这一个入口；现在 **325 条 headless 用例被逐条注册为 CTest 条目**，带分层标签
   与单例超时，并在 **Linux / Windows / macOS 三个平台的 CI job 上执行**，失败即 PR 红。门禁由
   36 条扩到 325 条（约 9.0 倍）后，此前"只在本地跑过、CI 从未触达"的用例首次进入必过集合。
3. **无障碍（ACC）保持完成态。** `version.txt` 的 1.5 里程碑把 "IAccessible 接口跨平台"与
   "内存泄漏检测、线程安全检测"并列；实现上，一套 `IAccessible` 门面 + 两个维护桥覆盖了三桌面平台
   （见第五章），本周期未发生能力回退。

综合评分（满分 5 分）：

- **架构设计 ★★★★☆**：平台/渲染二维正交、公共 API 面严格等于 Windows SDK、下游零感知——
  三点都做到了。扣分在 `src/` 内 Wine 派生文件与自研代码风格混编（3.4）。
- **可靠性 ★★★★☆**：核心路径已有 325 条 CI 门禁用例（三平台）+ 构建即测试 + valgrind 抑制基线；
  本周期修掉的 X11 事件未初始化外发与静态析构期 UAF 都是真缺陷。扣分在 23 个空实现里仍有
  真实功能缺口（滚动位块搬运、跨线程异步投递等，见 4.3），以及 25 处 UAF 这类问题**只有 valgrind
  能发现而 CI 不跑 valgrind**；另需留意 4.5 的**运行期静默失败面**（建原生控件窗口返回 `NULL`）。
- **工程规范 ★★★★☆**：文档体系完整且与代码同步、`license_CN.txt` / `license_EN.txt` 已含完整的
  第三方代码清单与 LGPL 义务说明。CI 已由"没有"变成"三条工作流"，本项原扣分点基本消除；
  余下扣分在**门禁覆盖面仍限于桌面三平台**（第八章风险 1）。
- **可维护性 ★★★★☆**：分层清晰、`doc/` 15 篇覆盖各子系统、API 清单可机械化重生成。
  扣分在单作者（bus factor = 1）。
- **测试保障 ★★★★☆**：327 个用例、325 条进门禁、跨平台同源用例、失败时打印用例日志并有
  平台化的 gdb 诊断步骤。扣分在 iOS/Android/OHOS 无自动测试，且集成级验证（真实 AT 客户端
  走查）仍是人工循环。

## 三、架构与实现现状

### 3.1 公共 API 面严格等于 Windows SDK

`include/` 下 44 个头文件与 Windows SDK 同名同结构：`windows.h` 聚合 `winuser.h`、`gdi.h`、
`sysapi.h`、`class.h`、`commctrl.h`、`unknwn.h`、`oaidl.h`、`oleacc.h`、`shlwapi.h` 等。

这条纪律的价值在于**下游零修改**：SOUI4 的代码直接 `#include <windows.h>`，不需要
`#ifdef` 分支。目录里没有 `swinx_*.h` 之类的扩展头；平台桥需要的内部助手
（如 ACC 的 `SwinxAccResolvePath`、`SwinxDispatchPendingWinEvents`）放在
`src/SwinxAccGlue.h`，明确**不对外导出**。本周期新增的键盘布局句柄编码约定同样遵守这条纪律：
它被放进**新建的内部头 `src/hkl.h`**，而不是像早先那样写进 `include/ctypes.h`——
后者是 `include/` 下唯一的非 guard `SWINX_*` 宏，属把内部约定漏进公共头的反例，已移除。
"新增能力不得往公共头里塞扩展"这条已固化在文档中。

### 3.2 五平台 × 两后端的实际编译归属

由各 `*.cmake` 的实际源文件清单核定（非文档声明）：

| 目标平台 | 平台适配层 | 渲染后端 | 构建脚本 | 平台专有依赖 |
|---|---|---|---|---|
| Linux（桌面） | `platform/linux` | `gdi/cairo` | `linux.cmake` | ALSA（可选） |
| macOS | `platform/cocoa` | `gdi/apple` | `macos.cmake` | Cocoa / CoreGraphics / **CoreServices** |
| iOS | `platform/ios` | `gdi/apple` | `ios.cmake` | UIKit |
| Android | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | Android NDK |
| OpenHarmony | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | OHOS NDK（`ace_napi`/`ace_ndk`/`native_window`/`hilog`） |

平台差异的收敛方式有两个层次。其一是"实现下沉"：`src/platform/<平台>/` 提供该平台的
实现，`src/*.cpp` 只写 Win32 语义。其二是"同一符号、分目录实现、链接期解析"：跨平台的
公共助手声明集中在 `src/SwinxUtils.h`（当前为 `swinx_messageBeep`），各平台目录给出
同名同签名的实现，`file(GLOB)` 只把当前平台的源文件放进构建，于是调用方（`src/sysapi.cpp`）
写的是同一个函数名，正文中不需要平台 `#ifdef` 分支。暂不实现的能力在
`platform/mobile/utils.cpp` 保留占位定义（返回 `FALSE`），以维持这一形态而不是退回 `#ifdef`；
移动端需要平台能力时则转发 `g_platformAPI`（`include/platform_api.h`，当前
`PLATFORM_API_VERSION = 3`；已登记 `MessageBeep` → `audio.messageBeep`，与 `PlaySound` /
`ShowSoftKeyboard` 同路），由宿主应用层补足平台差异。

**本周期新增的第三种形态：把"平台能力的差异"抽象成句柄族。** 键盘布局三函数
（`ActivateKeyboardLayout` / `GetKeyboardLayout` / `GetKeyboardLayoutList`）在四组平台适配器上
语义差别很大——Linux 是 XKB group、macOS 是 TIS 输入源、iOS 与移动端 OS 不允许 App 切换布局
（只有唯一布局）。swinx 的处理是：顶层入口（`src/sysapi.cpp` + `src/winnsl.cpp`）保持
Win32 的 HKL 语义，把平台差异压到各平台 `SConnection` 的三个同名方法里，**新增的 `HKL`
取值约定收在 `src/hkl.h`，四个平台共用一份**。这与 `SwinxUtils.h` 的思路一致，但作用对象从
"函数"变成了"类型编码"。同一周期还修掉两个相关缺陷：`HKL_PREV` / `HKL_NEXT` 按
`um\winuser.h` 的权威值更正为 **0 / 1**（原先误按 1 / 2 判定），以及 macOS 侧 `TIS*` API 的
链接归属（Xcode 12 起从 Carbon 迁至 `CoreServices`，`macos.cmake` 已补链接）。

### 3.3 第三方全 vendor 化

`thirdparty/` 内置 20 个组件（cairo、pixman、fontconfig、freetype、libpng、zlib、brotli、
expat、libxcb、xcb-util 家族、xcb-imdkit、xkbcommon、dbus-1.14.10 等），全部由顶层
`add_subdirectory(thirdparty)` 静态编入。

收益是**构建可复现与零版本风险**：目标机不需要预装任何图形/输入/无障碍库，也不存在
"发行版 cairo 版本不同导致行为漂移"。代价是 `thirdparty/` 下约 7,800 个文件进入仓库
（占仓库受版本管理文件数的 96.7%）。此外 vendored 库的**实际头文件即为契约**——文档已记录
"以 vendored 库的实际行为为准，而非上游文档"这一纪律；本周期修 X11 事件未初始化时，
判据也直接取自 libxcb 自身源码里"事件恒为 32 字节"的写死拷贝（见 6.5）。

### 3.4 遗留与自研代码的边界

代码来源可分为两段：`src/` 与 `include/` 内一批文件源自 Wine 的对应实现
（`include/winerror.h`、`cursoricon.cpp`、`safearray.cpp`、`profile.cpp`、
`malloc_impl.cpp`、`cmnctl32/listbox.cpp`、`uitools.cpp`、`list.h`、`cmnctl32/heap.h`，

**为什么上表第二、三行是"静默失败"**：`WC_EDITA` 这类**类名只是宏**，调用方引用的是
`CreateWindowEx` 这个**已定义**的函数，因此编译与链接都会通过，直到运行时才发现窗口类不存在。
**这是 swinx 目前唯一一类"静默失败"面，排查成本高于链接期报错**——若调用方不检查
`CreateWindowEx` 的返回值，现象是"程序起来了、界面是空的"。

**结论**：swinx 的完备度是"**承载用 SOUI 编写的应用**"这一目标下的完备度，**尚未达到

该目标在能力上可达——`ListBox` 已证明 Wine 控件可整体搬运，消息 / DC / GDI / 类注册这套地基
稳固——差距属**工作量而非架构不确定性**。

## 五、无障碍（ACC）实现现状

ACC 是本版本（1.5）明确列入交付口径的能力，实现已完整可查；本周期未改动 ACC 逻辑
（`objbase.cpp` 的 +47 行属于 BSTR 族补齐，与 ACC 无关）。

### 5.1 三层结构

```
   系统 AT（Windows Narrator / macOS VoiceOver / Linux Orca·accerciser）
        │
        ▼  平台无障碍协议：MSAA(COM) / NSAccessibility / AT-SPI2(D-Bus)
   平台桥   swinx：Windows 原生 oleacc ｜ cocoa:SNsAccessibility ｜ linux:SAtSpi
        │
        ▼  WM_GETOBJECT / LresultFromObject / ObjectFromLresult
   SOUI 侧  SHostWnd::OnGetObject → SAccessible（唯一 MSAA 门面）
        │
        ▼  IAccProxy（纯 SOUI 语义，不继承 IAccessible）
   控件      SWindow / SButton / SListView / STabCtrl …
```

关键约束：**swinx 不持有 `IAccessible`**。`WM_GETOBJECT` 往返由一张弱登记句柄表
（容量 256、FIFO 淘汰、**不 AddRef**）承接，客户端按 `(句柄, wParam)` 匹配解析；
`AccessibleObjectFromWindow` 把 OBJID 按 32 位有符号数放进 `LPARAM`（复刻真实 oleacc 的
符号扩展），`NotifyWinEvent` 在**事件产生时**对钩子做快照、无匹配即丢弃，投递由消息泵异步完成。

### 5.2 三平台的接入方式

| 平台 | MSAA API 提供方 | 桥文件 | 下层协议 | 桥是否持有对象 |
|---|---|---|---|---|
| Windows | 系统 `oleacc.dll` / `oleaut32.dll` | 无（原生） | MSAA/COM | 不适用 |
| macOS | swinx `oleacc.cpp` + `objbase.cpp` + `variant.cpp` | `platform/cocoa/SNsAccessibility.mm` | `NSAccessibility` | 不持有（身份壳） |
| Linux | 同左 | `platform/linux/SAtSpi.cpp` | `AT-SPI2` over D-Bus | 不持有（确定性路径编码） |

两个桥的共同策略是**不做对象缓存**：Linux 桥把对象路径按
`/org/a11y/atspi/accessible/w<hwnd>_c_<i>_<j>` **确定性编码**，每次请求按路径从窗口根重新
导航一遍（O(深度) 次调用），换来"绝不访问已销毁控件的悬垂指针"；macOS 桥用不持 COM 的
身份壳 + 缓存。共享的路径下钻内核是 `SwinxAccResolvePath`（`oleacc.cpp`），两平台复用。

### 5.3 非 MSVC 工具链上的 COM 实现

gcc/clang 不支持 `__uuidof` 关键词，也不提供 COM 运行时。swinx 用四件事补齐：

| 补齐项 | 位置 | 机制 |
|---|---|---|
| 接口声明宏 | `include/basetyps.h` | `DECLARE_INTERFACE_`/`STDMETHOD`/`THIS_`/`PURE` 的 C 与 C++ 两套展开 |
| IID 获取 | `include/guiddef.h` | `__uuidof(X)` 与 `__suidof(X)` **都定义为 `X::GetIID()`**；配合 `DECLARE_CLASS_SIID` 在每个接口内生成静态函数——把编译期类型→IID 映射降级为普通静态函数调用 |

### 6.2 线程安全：CountMutex

Win32 的消息派发语义要求"进入窗口过程前释放系统内部锁"。swinx 用 `CountMutex`
（`src/countmutex.h`，51 行）适配：在 `CallWindowObjProc` 与消息泵的 `WM_TIMER` 回调处
`FreeLock()` → 调用业务回调 → `RestoreLock(preLock)`，把锁深度**降到 0 再恢复到原深度**。

这不能靠 `std::recursive_mutex` 单独完成（标准设施没有"一次清空、按值恢复"），
故保留自定义类。约束已文档化：`FreeLock`/`RestoreLock` 必须**同线程配对**、
`preLock` 原样回传、不得交叉嵌套；**回调窗口期内对象处于无锁状态**是与真实 Win32 一致的
特性——新增回调窗口期调用点时必须显式意识到这一点。

### 6.3 内存与泄漏检测

- `src/malloc_impl.cpp`（461 行）提供 `IMalloc` 实现，作为 `CoGetMalloc` 的可替换分配器。
- `valgrind-linux.supp` 抑制基线：记录 valgrind 已知误报（如 glibc AVX2 `wmemcmp` 的 32 字节块
  越界读——ifunc 分派绕过 valgrind 拦截器导致的假阳性）。抑制项附带成因说明，而非静默关闭。
- **判读纪律（本周期补强）**：① valgrind 报告需先区分"fork + `_exit` 继承的快照"与"本进程
  真实泄漏"——`test_flock.cpp` 的三个 `fork()` 子进程各自报出的 95,000 字节 `definitely lost`
  三段逐字节一致，属继承堆快照而非泄漏，跑本工程应加 `--child-silent-after-fork=yes`；
  ② X11 请求是**共享输出队列**，"未初始化字节"的报错栈顶只是最后调 `flush` 的人
  （cairo 常被误指），不能照栈顶归因。
- **静态生存期**：`src/sharedmem.h` 的 flock 全局登记表位于头文件中、且会被**静态析构路径**
  （`GLobalHandleTable::~` → `SharedMemory::~` → `~TNamedSemRwLock`）访问。由于该 inline
  函数的静态局部量由首次初始化它的 TU 注册析构，而可执行文件的 `__cxa_finalize` 恒早于
  动态库的 fini_array，"exe 先销毁表、库再析构对象"的顺序不可修复 ⇒ 该表改为
  **leak-on-purpose 的单例对象**（互斥量与表收成同一类的两个成员，按声明逆序析构），
  运行期行为不变，退出时多一份空表计入 still-reachable。

## 八、风险与限制清单

按优先级排序：

1. **门禁覆盖面只到桌面三平台**（本版最高；原"无 CI 门禁"风险已按此收窄）。CI 现有三平台 job
   均由 `submodules: recursive` 检出 swinx 并跑 325 条门禁用例，**但 iOS / Android / OpenHarmony
   无任何自动构建与测试**：这三端的回归完全依赖人工，而它们恰恰是 vendor 依赖最多、平台
   API 最不标准的端（OHOS NDK、Android NDK、UIKit）。至少应加"交叉编译不回归"的 job。
2. **接口面缺口：迁移既有 Windows 程序所需的"原生控件 / 窗口菜单栏 / 资源对话框"未建立**
   （4.5）。内置注册的窗口类仅 `Static` / `Button` / `ListBox` 三个；`Edit` / `ComboBox` /
   `ScrollBar` 与全部公共控件无实现；窗口自己的菜单栏（`SetMenu` / `GetMenu` / `DrawMenuBar`）
   无声明；无对话框实例化 API（`DialogBoxParam` 族）。**量级远大于声明层面的缺口**，且其中
   "建原生控件窗口"是**运行期静默返回 `NULL`**（见 4.5）。
   另有**声明层面的 5 项 API 缺口**（4.3 类别三）：`ScrollWindowEx`、`SendNotifyMessage{A,W}`、
   `SetWindowExtEx`、`SetMenuItemBitmaps`，按是否出现调用方逐个排期即可。本周期已关闭 5 项：
   键盘布局族 3 项、`DragFinish` 1 项、`AdjustWindowRectEx` 1 项；并把 `IsWindowUnicode` 从
   "可能不正确"澄清为刻意语义——**本版已无"被识别为不正确"的接口**。
3. **ACC 扩展面**（5.4）。Linux 侧缺 `Text`/`Value`/`Selection`/`Table` 等 10 余个
   AT-SPI2 接口，macOS 侧缺 `selectedChildren`/`rows`/`minValue` 等。当前 AT 客户端
   能导航对象树但读不到文本与数值内容。**属能力边界而非缺陷**，但直接决定"屏幕阅读器
   能否真正朗读应用内容"。
4. **ACC 事件归因粒度**（5.4 末条）。桥未使用 `idObject`，事件止于窗口级。可经
   `AccessibleObjectFromEvent` 解析细化，属未实现路径。
5. **参数化用例未被完整注册**（6.1）。`gtest_add_tests` 在配置期用正则扫源码，`TEST_P`
   拆不全（官方文档明说）。当前测试集未用 `TEST_P`，故暂无实际影响，但新增参数化用例时
   必须单独核验注册结果。
6. **HKL 低字语义与真实 Win32 不一致**。真实 Windows 的 `HKL` 低字是 `LANGID`
   （`third-part/richedit41` 就用 `LOWORD(GetKeyboardLayout(0))` 取语言 id），而 swinx 的
   HKL 是"索引 + base"的内部编码，不满足这一约定。当前仅在 `SOUI_BUILD_RICHEDIT`（默认 OFF
   且只在 Windows 暴露）下会被触达，属潜在项。
7. **macOS 跨进程 HWND IPC 空缺**。已从"未知"变成"有结论"（见新增调研文档）：照搬
   "HWND 即跨进程窗口句柄"的现有设计在 macOS 上**不成立**（HWND 是进程内对象指针），
   但基于 HWND 语义实现 IPC **可行**，前提是把契约改为"全局窗口 ID ↔ 进程内 HWND"映射；
   同族进程互发消息可行、跨进程按类名/标题查找需新增注册表、向任意第三方应用窗口发消息
   不可行（且不合规）。现有 shm / 具名对象 / fd 消息泵三层设施可复用。
8. **`thirdparty/` 体量**。7,843 个文件进入版本库，占仓库受版本管理文件总数（8,111）的
   **96.7%**；对 clone 体积与检索体验有实际影响。是否接受这一取舍需明确定调（当前是接受的）。
9. **OHOS 深度适配**（延续项）：沙箱下 `/tmp`、`shm_open` 可用性待真机验证；
   ACC 在 OHOS 上不启用。
10. **单作者**（bus factor = 1）。

已关闭项（保留记录，便于后续版本对照）：许可合规文本缺失（7.1，已补齐中英双份清单）；
键盘布局族 3 项 + `DragFinish` 1 项功能缺口（4.3）；`IsWindowUnicode` 语义存疑（4.3，已澄清）。

## 九、建议路线图（按性价比排序）

1. **给移动端与 OHOS 加"交叉编译不回归"CI job**（关闭风险 1）。Android NDK 与 OHOS NDK 的
   交叉编译可在 Linux runner 上完成，成本远低于真机测试；先把"能编过"这条底线自动化，
   就等于把三端的构建回归纳入门禁。`fun_test` 的门禁骨架已经就绪，无需改测试代码。
2. **把 `api_scan.py` 接成覆盖门禁**（关闭风险 2 的"继续扩大缺口"路径）。脚本已可机械化产出
   `api_scan.json`，在 CI 中记录分级数量并对"实现面回退"直接失败即可，成本极低。
3. **ACC 扩展面按需推进**（关闭风险 3、4）：优先 `Value`（进度条/滑块可朗读）与
   `Text`（编辑类控件可朗读），再评估 `Selection`/`Table`；随后用
   `AccessibleObjectFromEvent` 把事件归因细化到节点级。
4. **按项目需要补齐"迁移面"**（关闭风险 2，见 4.5）：建议优先级为 ①**窗口菜单栏**
   （`SetMenu` / `GetMenu` / `DrawMenuBar`——弹出菜单机制已完整，缺的是窗口侧挂载）；
   ②**常用原生控件**（`Edit` / `ComboBox` / `ScrollBar`，可沿 `ListBox` 的 Wine 搬运路径）；
   ③**公共控件**与 `InitCommonControls(Ex)`；④**资源对话框**（`DialogBoxParam` 族）。
   声明层面的 5 项小缺口（`ScrollWindowEx`/`SendNotifyMessage{A,W}`/`SetWindowExtEx`/
   `SetMenuItemBitmaps`）随调用方出现时顺带补即可。
5. **按调研结论实施 macOS 跨进程 IPC**（关闭风险 7）：按文档 8.3 的落地顺序推进，
   传输通道建议选 UNIX domain socket（而非 Distributed Objects）。
6. **`HKL` 语言 id 语义**（关闭风险 6）：在 `GetKeyboardLayout` 的返回值上补 LANGID
   映射，或明确记录"不支持 `LOWORD` 取语言 id"。
7. 其余：`thirdparty/` 取舍定调、OHOS 真机核验。

## 十、结论

swinx 1.5 用约 **16.3 万行**自研与派生代码（`src/` + `include/`，不含 vendor 的 `thirdparty/`）
完成了两件事：把 Win32 API 语义搬上 5 个平台 2 个渲染后端，并让这套语义在真实的重型消费者
（SOUI4 及 20+ 示例工程）面前站得住。架构上的两条主线——**公共 API 面严格等于 Windows SDK**
（下游零 `#ifdef`）与**平台/渲染二维正交**（新增平台与新增后端互不牵连）——是本项目最重要的
设计资产，也是它能从桌面延伸到移动端与 OHOS 而结构不变的原因。

本基线的实质进展集中在**验证能力**而非新功能：`api_scan` 给出的 **913/1,042 有定义、
884 项完整实现**（另有 6 项部分、23 项空实现/语义桩，仅保留声明 129 项、实际未提供 123 项）
继续作为覆盖率基准；而 `fun_test` 的 **325 条 headless 用例已逐条注册为 CTest 门禁，
并在 Linux / Windows / macOS 三个平台上随 PR 自动执行**——测试从"本地跑得起来"变成
"CI 拦住回归"，这是把项目从"作者的工程"推向"可被他人接手与验证的工程"的关键一步。
无障碍（ACC）保持三桌面平台的完成态，第三方许可清单已补齐中英双份。

技术侧的待办方向清楚、边界明确：**声明层面的 API 缺口已收缩到 5 项**、`IsWindowUnicode` 的疑点
已澄清、macOS 跨进程 IPC 已从"未知"变成"有结论有方案"；但**接口面层面仍缺"原生控件库 /
窗口菜单栏 / 资源对话框"三块**（见 4.5）——它决定"既有 Windows 程序能否零成本迁入"，
**当前答案是还不能**，这是本报告需要向外部准确传达的能力边界。**本版最需要补的一块是门禁的覆盖面**——
325 条门禁只覆盖桌面三平台，iOS / Android / OHOS 仍无任何自动回归；这属于流程与自动化成本，
不是不确定性问题。
